## Accepted device-role decision

The user confirmed that phone-created tasks save locally and sync through the relay while the Mac is asleep. The Mac is the primary workspace/compute device; ordinary writes from trusted devices do not require its acknowledgement. See the [accepted architecture decision](2026-09-12-wellspent-local-first-architecture.md#accepted-decision-mac-centered-independently-writable-devices).

R01 is partially resolved: device roles are accepted; record scope and migration remain open. Acceptance for the future replica implementation: with the Mac disconnected, create a task on the phone, terminate/reopen after local commit, upload when able, and deliver it to another online trusted peer. Reconnect the Mac and observe that same task once, including after a lost upload acknowledgement/retry. Also verify local save and eventual upload with the phone offline. This is planned evidence, not an executed test.

| R08 — Which exact suite, encoding, nonce, and authorship scheme? | Repeated record edits and restored devices can break naive nonce policies; shared epoch keys do not prove device authorship. | Pin candidate crates/features; review advisories, audit scope, license and RNG support. Unlocks a versioned experimental format. |
| R09 — Can native keys and bindings support the design? | Hardware support and Rust P-256 support do not prove external-keystore HPKE works. | Bind one Rust operation/error/callback through Swift and Kotlin; package actual targets; separately test P-256 decapsulation through OS-owned keys without export. | Software keys first. An authenticated identity/suite migration is required for hardware keys. Unlocks platform and minimum-OS commitments. |
| R10 — Where is private context filtered and who can bypass it? | Hosted programmatic tools and unrestricted executors can leak data beyond the visible prompt. | Seed a synthetic vault with disallowed canaries. | R11 — What survives sleep, reconnect, cancellation, and approval delays? | Session resumption does not prove external actions execute once. | Kill executor and application at each boundary: before call, after provider success, before result persistence, while approval waits, after denial/cancel. No account-access or automated key-provisioning guarantee yet. |
| R13 — What is actually delegated to Calendar/Linear? | Current Calendar publication is not personal-calendar availability; fresh OAuth scopes and Linear access are new work. | Define a resource-scoped read manifest and one immutable calendar-hold proposal. One read-only provider first after fixtures; add the second only to test incremental value. |
| R14 — What survives subscription end or relay loss? | Local-first credibility depends on export and restore, while history and storage cost must be bounded. | Restore an encrypted backup to a new local device/reference relay; model quotas, retention, tombstones, long-offline peers, and garbage collection. | Local read/edit/export remain available. | R15 — Does the planner help, at acceptable cost? | A large capability catalog can precede proof of usefulness. | Compare a manually prepared three-hour plan with a fixture-backed agent plan, then selected live reads. ## Technology findings

These checks narrow the research queue. They do not select production dependency versions or establish an audited end-to-end construction.

| Candidate | What current primary sources establish | Remaining evidence |
| --- | --- | --- |
| HPKE / Rust `hpke` | RFC 9180 provides standardized key-encryption constructions. The Rust project supports X25519/P-256 and test vectors; its README does not claim a paid audit and identifies an older internal review. [RFC](https://www.rfc-editor.org/rfc/rfc9180.html), [rust-hpke](https://github.com/rozbb/rust-hpke). | Exact pinned version/dependency review, authentication mode, membership binding, hardware key-provider interface. Avoid calling the current crate fully audited. |
| RustCrypto primitives | AEAD implementations exist; XChaCha20-Poly1305 offers extended nonces. Audit statements apply to specific implementations/versions, not the whole ecosystem. [AEAD repository](https://github.com/RustCrypto/AEADs), [ChaCha crate](https://docs.rs/chacha20poly1305/latest/chacha20poly1305/). | Select only needed crates. Review `hkdf`, `sha2`, `zeroize`, `secrecy`, OS RNG/getrandom and signing dependencies; avoid duplicating HPKE internals. Argon2id research waits for password recovery scope. |
| UniFFI | Swift/Kotlin bindings are supported; shipping the compiled library remains application work. Development docs describe foreign traits and partial Swift 6 support. [Guide](https://mozilla.github.io/uniffi-rs/), [foreign traits](https://mozilla.github.io/uniffi-rs/next/foreign_traits.html), [Swift support](https://mozilla.github.io/uniffi-rs/next/swift/overview.html). | Pinned stable generator/runtime compatibility, Apple packaging, Android ABIs, strict Swift concurrency, callbacks/cancellation, errors, buffer copying, and lifetime tests. Development docs are not a promise for a selected release. |
| Apple device keys | Secure Enclave supports P-256 agreement/signing with protected private-key operations. [Key agreement](https://developer.apple.com/documentation/cryptokit/secureenclave/p256/keyagreement), [key protection](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave). | Physical Mac/iPhone availability; separate agreement/signing key roles; lock/reboot, access control, persistent references, unavailable hardware, and migration from software identity. |
| Android device keys | Keystore hardware residency varies. StrongBox is optional; key-agreement purpose was added at API 31. [Keystore](https://developer.android.com/privacy-and-security/keystore), [API addition](https://developer.android.com/sdk/api_diff/31/changes/android.security.keystore.KeyProperties). | Minimum Android version; observed key security level; TEE/StrongBox fallback; invalidation; HPKE interoperability. Attestation proves neither user consent nor vault membership. |
| Expo Modules | Official Swift/Kotlin module boundary supports the proposed wrapper. [Overview](https://docs.expo.dev/modules/overview/). | Coarse record/batch interface, native-only secret handling, asynchronous error/cancellation behavior. Profile attachment copying before considering Nitro. |
| SecureStore | Keychain-backed storage on iOS and Keystore-encrypted storage on Android; uninstall, backups and biometric changes affect availability. [SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/). | Native retrieval without sending long-lived keys through JS; reinstall/backup/lock matrix; key invalidation recovery. Stored secret bytes are not a non-exportable asymmetric identity. |
| SQLCipher | Expo SQLite documents SQLCipher with native configuration/builds, unavailable in Expo Go. [SQLCipher](https://docs.expo.dev/versions/latest/sdk/sqlite/#sqlcipher). | Installed SDK compatibility; native Swift distribution choice; random DB keys, transactional migration, WAL/sidecars, backup/restore, wrong-key failure and restart. |
| Expo Crypto | Current documentation includes randomness, hashing and AES-GCM. [Crypto](https://docs.expo.dev/versions/latest/sdk/crypto/). | Check the installed SDK before relying on APIs. It does not supply Wellspent membership/recovery semantics. |
| Quick Crypto | The maintained project describes C++/JSI/Nitro implementation and incomplete Node crypto coverage. [Repository](https://github.com/margelo/react-native-quick-crypto). | Exact algorithm/encoding vectors if compared. No current reason to create a second TypeScript protocol implementation. |
| libsignal | External use is unsupported and interfaces may change. [README](https://github.com/signalapp/libsignal#overview). | Study identity/transfer/ratchet design; keep it out of the dependency plan. |
| MLS / OpenMLS | RFC 9420 supplies group key evolution; forward secrecy depends on deleting old secrets and recovery from compromise on appropriate updates. OpenMLS implements MLS, but its current supported-platform table does not establish tested mobile acceptance. [RFC](https://www.rfc-editor.org/rfc/rfc9420.html#section-16.6), [OpenMLS](https://github.com/openmls/openmls#supported-platforms). | Reopen only if group evolution/forward-secrecy requirements justify complexity. Retained vault history and recovery still need their own policy; adopting MLS does not erase old copies. |

## Outcome-sized research sequence

These are deferred research tasks, not the immediate workflow-capture backlog and not tasks executed in this pass. Resume them when the product needs encrypted replication or provider planning. Each gate records pass/fail/unrun evidence; a happy-path demonstration is insufficient.

### Gate 0 — Decide the product's privacy contract

Scope: R01–R05. Output five short decisions and an updated threat model, including a data-classification sheet and explicit browser position. Preserve the current product and queued data. No migrations or API calls. Acceptance: a reader can answer what survives loss/revocation, what the server can read, who admits devices, and what offline users can do. If a choice is unresolved, name it rather than inserting a convenient assumption.

### Gate 1 — Written state machine and adversarial transcripts

Depends on Gate 0. Scope R02/R03/R04/R06/R08. Define genesis, pairing, membership transitions, operation identities, epoch changes, recovery authority, replay and conflict outcomes. Use synthetic A/B/C devices and a malicious relay. Acceptance: enumerate legal/illegal transitions and expected observations for substituted keys, duplicate pairing, concurrent membership edits, stale writers, rollback/forks, recovery after rotations and version downgrade. Obtain protocol review before presenting these rules as secure.

### Gate 2 — Rust CLI plus one durable local replica

Depends on Gate 1 and R07's ownership decision. Create the small crypto component and CLI in a future implementation task. Simulate A encrypting, B failing before pairing, approved B decrypting/editing, A reading, B removal/rotation, B failing on adopted-new-epoch records, and C recovery. Add the hostile transcripts and process-kill/backup-restore/retry cases. A relay directory is enough.

Acceptance: reconstruct the same local projection after restart; preserve unsynced originals; reject corruption/substitution/replay according to the specification; demonstrate historical exposure limitations explicitly. Use reproducible fixtures and deterministic test randomness only in test code. Freeze versioned experimental vectors after review; a prototype pass does not freeze production format or authorize use on real vaults.

### Gate 3 — FFI and native key/storage feasibility

Binding packaging can be explored with non-sensitive fixtures alongside Gate 2. Before the production API is frozen, pass one operation and structured error through native Swift macOS and Swift/Kotlin Expo adapters. Test callbacks, cancellation, threading and secret-copy boundaries. Verify SQLCipher and native secure storage with lock/reboot/reinstall/restore scenarios. Run hardware P-256/HPKE as a separate experiment, not a rewrite of the software prototype.

The September 17 distribution target is Mac App Store plus signed direct download, with app stores preferred where feasible. Frontload a sandboxed Mac binding and synthetic CLI/helper handoff using the [distribution feasibility criteria](2026-09-17-wellspent-system-design.md#distribution-target-and-helper-feasibility). Record channel-specific installation, signing, consent and lifecycle evidence; an external development runner or successful Rust compilation does not establish store compatibility.

Acceptance: evidence per macOS, physical iPhone, physical Android; supported ABI/OS matrix; exact toolchain/dependency versions; explicit failure/fallback policy. Reuse existing native UI. Build success alone does not prove key lifecycle or durable sync.

### Gate P — Planning value and disclosure enforcement

Can run with fixtures after Gate 0 without waiting for encrypted replication. First assemble a small selected project/context export, Calendar fixture and Linear fixture. Produce a three-hour plan and show the source/time range for each recommendation. Store a disclosure manifest and test out-of-scope canaries. Use application-owned function handlers first if Mac executor isolation is unproven.

Acceptance: useful plan compared with a manual baseline, no unsupported claims, no disallowed content in outbound payloads, clear missing/offline data, measured total latency/usage. Then authorize one live read integration and compare. Add one calendar hold only after exact-payload approval and idempotent execution/reconciliation are implemented. No ambient observation or automatic messaging.

### Gate 4 — Relay and migration rehearsal

Depends on successful protocol/storage gates. Scope authenticated opaque storage, per-account routing, limits, envelope delivery, resumable upload/catch-up, acknowledgement loss and local export. Use a disposable synthetic dataset; model pagination gaps, malicious omissions, attachment limits, stale clients and garbage collection. Rehearse legacy import with browser pending commands and historical records.

Acceptance: both replicas recover after restart and converge or show the specified conflict; full relay DB/log/backup inspection finds no canary vault plaintext or keys; unsupported clients fail safely; migration retains originals until verified. Leakage inspection is not a cryptographic proof. No production import, deletion, dual-write cutoff or deployment is authorized by this document.

### Gate 5 — Cross-device approval and one offline cloud automation

Depends on Gate P and the trusted-device/approval model. Example: a synthetic P1 assignment proposes a focus block. Define trigger deduplication, explicit delegated state, grant expiry, approval deadline, action execution and provider reconciliation. Test with all devices offline, Mac asleep, expired OAuth, duplicate webhooks, changed Calendar state and duplicate phone approvals.

Acceptance: an action runs only within its grant and exact approval; expired/changed actions cannot execute; provider uncertainty stays visible; tasks/results remain recoverable without the original agent session. Production integration writes need a separately authorized task.

### Gate 6 — Production hardening and portability

Before strong E2EE claims: exact dependency/audit review, property/convergence tests, parser fuzzing, cross-platform vectors, fault injection, account isolation, signed update/release process, recovery usability, encrypted export/restore, logging/retention review and external cryptographic/security assessment. Record remaining metadata and historical exposure in product language. Decide commercial relay/history limits and license scope after technical portability is demonstrated.

## Deliberately deferred

Double Ratchet, MLS implementation, LAN/P2P sync, password-only recovery, universal agent catalogs, default subagents, Nitro migration, full ambient activity collection, arbitrary SQL/file tools, team vaults, and a public self-hosted relay release are outside the first prototypes. Reopen each only when a concrete requirement or measured bottleneck justifies it.
